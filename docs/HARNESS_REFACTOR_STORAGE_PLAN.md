# Harness 重构 · 存储搬迁计划

2026-11-11 · 决策已定，尚未执行，产品代码未动。本文记录用户在同日两轮讨论里就「存储改为追加式」定下的七项决定、对照源码得出的现状、拟定的落盘布局和实施步骤。难以回退的部分记在 [ADR 0007](adr/0007-append-only-run-log-run-id-and-readonly-delegation.md)，它已于 2026-11-11 被用户接受（`status: accepted`）；接受时确认的只是运行标识一侧的取值，本文「仍待处理」里的条目和标「拟定」的内容没有随之确认。文中行号对应提交 `39d7299`。

本文只覆盖存储。运行标识和只读委派在 [运行标识、存储搬迁与只读委派计划](HARNESS_REFACTOR_RUN_ID_STORAGE_DELEGATION_PLAN.md) 里。本文里凡是提到「运行标识」的地方都只引用 ADR 0007 第五、第六项的结论；信封里运行标识和步号的字段名取那份计划 A1 节拟定的名字，不在这里另定。两份文档在存储上如有出入，以本文为准，因为后三项决定是在 ADR 0007 起草之后才定的。

本文与 [拆分阶段实施计划](HARNESS_REFACTOR_SPLIT_PLAN.md) 的关系：拆分阶段不改持久化数据的形状，也不增减、不调换 `store.save()` 和 `ledger.put()`。本文全部是持久化改动，属于「迁移」阶段，排在拆分和运行标识之后。

文中的内容分三种，写法上分开：**已定**是用户选的；**拟定**是我按源码提出的做法，没有经用户确认；**推算**是按代码路径和一次真实任务的计数算出来的，没有实测。

## 已定的七项决定

| # | 议题 | 决定 |
| --- | --- | --- |
| 1 | 目标形态 | 回执、请求与用量、压缩记录、活动事件、额度预占改为每个功能一份 JSONL 追加日志；检查点单独存成小文件，整份替换；业务状态留在主文件。 |
| 2 | 落盘可靠性 | 分两级。回执的意图、结果、applied 标记，额度预占，检查点逐条 fsync；请求状态、用量、展示用的预算、活动事件只追加不 fsync，丢了按「用量未知就保持未知」处理。 |
| 3 | 版本与回退 | 搬迁写 `engineering-v2.json` 和日志目录，`engineering-v1.json` 原样留作备份。降级后看不到搬迁之后的进度。 |
| 4 | 排期 | 排在拆分之后的迁移阶段，日志信封与运行标识一起设计。开工前先在隔离资料目录测出现有实现的落盘次数、字节数和耗时。 |
| 5 | 主文件的范围 | 累计额度、活动事件、`contextRuntime` 的请求、压缩、操作和回执视图不再写进主文件，启动时从日志重放到内存里原来的位置，`store.data` 的形状不变。变更登记 `project.changes` 留在主文件。 |
| 6 | 保留与折叠 | 功能进行中日志不删、不折叠。最终验收之后写一条摘要并封存日志，之后不再加载，也不自动删除；资料目录超过阈值时界面提示，由用户手动清理。内存里的投影沿用现有上限。 |
| 7 | 正文去重 | 放在落盘层：日志行里的文件正文和命令快照正文换成 sha256 引用，正文按哈希各存一份。内存里的回执对象、两个哈希、各项校验和 `schemaVersion` 都不变。 |

第 1 至第 4 项的理由和没有采用的做法已写在 ADR 0007。后三项没有采用的做法：

| 议题 | 没有采用 | 原因 |
| --- | --- | --- |
| 主文件的范围 | 主文件里留一份定期快照 | 同一份数据存两处，要另外定义以谁为准，崩溃后两处不一致时没有判据。 |
| 主文件的范围 | 变更登记也外置 | 界面的「代码变化」页要展示前后全文（`EngineeringPage.tsx` 第 2136–2156 行），得加 IPC 并改界面；`files.ts` 第 253–254 行在验证准备时要拿登记里的 `after` 与磁盘内容比对，也得改成读外置正文。 |
| 保留与折叠 | 按大小分段滚动 | 要定义检查点覆盖到日志的哪一行；终结回执在功能完成之前都可能被对账读到，不能随旧段删除。 |
| 保留与折叠 | 沿用现有上限，超出就重写文件 | 不再是纯追加；截断会丢掉用量合计。 |
| 正文去重 | 不去重，只靠增量行 | 每条命令回执仍要追加前后两份工程快照。 |
| 正文去重 | 换回执合同版本，回执里不存正文 | 要改 `receiptIntentHash`、`assertFileReceipt`、`assertCommandResult` 和 `checkpoint-version.ts` 的白名单，两套校验长期并存，而且把存储格式和工具合同版本绑在了一起。 |

第 7 项能成立的依据：`receiptIntentHash`（`receipt-ledger.ts` 第 35–38 行）和 `sealReceipt`（第 39–41 行）都是对内存里的回执对象算的，`validateReceiptRecord` 也是对读回内存的对象校验。只要读回时把引用还原成正文，校验看到的对象与今天逐字相同。这一点只读了代码，没有运行。

## 落盘布局（拟定）

```text
<userData>/
  engineering-v1.json                 旧主文件，搬迁后不再读写
  engineering-v2.json                 新主文件，仍用「临时文件、fsync、改名」
  engineering-runs/<范围>/            范围 = sha256([项目 id, 功能 id])，与下面两个现有目录同一算法
    log.jsonl                         功能日志
    checkpoint.json                   检查点，整份替换
    bodies/<sha256>                   外置的正文
  engineering-runs/<项目范围>/log.jsonl   项目日志，放没有功能归属的记录
  engineering-artifacts/<范围>/       现有，不动
  engineering-commands/<范围>/        现有，不动
  model-traffic-v1.json               现有，不动
```

正文目录按功能分开而不是全局共用，代价是跨功能不去重，好处是封存和清理都以功能目录为单位。

**日志行。** 每行一个 JSON 对象，信封字段按 ADR 0007 第四项：范围、运行标识、步号、记录种类、时间，另加行格式版本。读取时只容忍最后一行不完整（丢弃它）；中间任何一行解析失败都按台账损坏处理，停下等待核对，不跳过。

**记录种类与可靠性等级。**

| 种类 | 内容 | 等级 | 重放到 |
| --- | --- | --- | --- |
| 回执 | 一次 `put` 之后的整条回执，正文已换成引用 | 逐条 fsync | `receiptJournals[key]`（同一逻辑调用后写的覆盖先写的）和 `contextRuntime.receipts` |
| 额度预占与结算 | 请求、工具各一次的预占；活动时间的预占、续约、结算；用户调整额度 | 逐条 fsync | `feature.runtimeBudget` |
| 请求 | 请求记录的建立、状态变化、用量 | 只追加 | `contextRuntime.requests`（最近 200 条） |
| 压缩、操作、预算 | 各自的记录 | 只追加 | `contextRuntime.compactions`（64）、`operations`（100）、`latestBudget` |
| 活动事件 | 现有 `ExecutionEvent` | 只追加 | `project.events`（最近 1200 条） |
| 摘要 | 最终验收时写的一条合计 | 逐条 fsync | 不重放，封存后只读这一行 |

回执每次 `put` 写整条而不是只写变化的字段，重放规则因此只有「后写覆盖先写」一条；整条回执去掉正文后只剩标识、参数、状态和输出。「只追加」的记录只要每条都同步写出、不在进程内攒批，进程崩溃时就不会丢，写进内核缓冲的内容会留下；丢失只发生在系统崩溃或断电时。

`contextRuntime` 里没有被第 5 项点名的字段（`manifest`、`manifests`、`status`、`reason`、`view`）怎样放，实施时逐字段核对：`view` 由检查点推导（`context-session.ts` 第 15–21 行），可以不落盘；其余几个字段的读取方没有逐一查过。

**正文外置。** 写日志行之前，先把这几处的字符串写进 `bodies/`，行里只留 sha256：`file.before`、`file.after`、`args.content`，`command.before.texts` 和 `result.command.after.texts` 的每个文件，`result.command.changes` 的前后文。正文文件用「临时文件、fsync、改名」写入，已存在同名文件就跳过。读回时按引用取正文并复算哈希，缺失或不一致时这条回执按不可核对处理，走现有的 `RecoveryRequired`。外置的是内存里的回执对象上已有的字符串，也就是今天会写进 `engineering-v1.json` 的同一份内容，不引入新的未脱敏路径。

按 pomodoro 的实测推算：不外置时一条命令回执写 4 行，意图行和 running 行各带一份快照，结果行和 applied 行各带两份，共约 0.9 MB；外置后 14 个文件的正文只存一份（134,661 字节），之后只有被命令改动的文件才新增正文，行里每个文件只剩一个引用。

**推算的写入量。** 同一次任务（72 次请求、225 次工具调用）搬迁之后：功能日志约 4800 行，不含正文约 2～5 MB；主文件写入不超过工具调用数加业务状态变化的次数，实际只有写文件和命令调用才写；带 fsync 的小追加约 900（回执）+ 300（额度预占）+ 最多 3600（时间续约）次，另有每步一次的检查点替换。时间续约那一项见「仍待处理」。

## 一次落盘提交多样东西的地方

今天任何一次 `save()` 都把内存里所有未落盘的改动一起提交。拆成多个文件以后，这种捎带不再发生，下面几处要逐个处理。这一节是这份计划里风险最集中的部分。

**活动事件捎带业务状态。** `store.event()` 末尾直接 `this.save()`（`store.ts` 第 259 行）。很多调用点先改业务状态再发事件，例如最终验收：`f.stage = 'done'` 之后紧跟 `store.event(p, 'accepted', …)`（`service.ts` 第 2407–2408 行）。事件改成只追加之后，这类调用点如果后面没有显式的保存，业务状态就不会落盘。62 处 `store.event(` 要逐个核对；回执 `put`、额度预占、请求记录这些改走日志的落盘点同理。步骤 0 的测量顺带产出这张清单。

**回执投影。** `applyReceiptProjection`（`execution-recovery.ts` 第 59–84 行）在一次落盘里同时改变更登记、检查点的命令证据、验证准备的 `actions` 和回执的 applied 标记，失败时整体回滚。拆开后它们分属主文件、检查点文件和日志。拟定的顺序是主文件和检查点先写，applied 标记最后写；崩溃落在中间时，重启后这条回执仍是未应用，投影会重做一遍。重做要求投影幂等：变更登记是覆盖写，命令证据有 `logicalCallId` 去重，`created:` 有 `includes` 判断，这三处已经幂等；第 81 行 `attempt.actions.push(receipt.tool + ': ' + …)` 没有去重，重做会多出一条，要先补上判断。

**交接。** `prepareRuntimeHandoff`（`service.ts` 第 576–606 行）一次落盘同时写原件、运行策略、模型、额度、交接记录、新检查点、关闭后的台账和 `contextRuntime`，失败整体回滚。拆开后要定一个提交点和重启后的补全规则，本文没有设计，列在「仍待处理」。

**检查点的删除。** `finish`（`service.ts` 第 1655 行）、`invalidate`（第 1794 行）和第 2131、2633 行删除检查点，其中 `finish` 不立即落盘，由随后的业务保存一并提交。分文件后要定先后：先提交业务状态再删检查点文件，崩溃后会留下一个属于已推进功能的旧检查点文件，续接入口要能识别并丢弃它。

**检查点与视图。** `saveCheckpoint` 同时改 `contextState.view`，`featureReceiptLedger` 同时重建回执视图。两者都是推导出来的，重放时重建即可，不构成新的中间状态。

## 实施顺序（拟定）

整个搬迁作为一个版本发布，中间提交不发布。中间提交产生的资料目录格式不完整，开发期间只对着 `COPROJER_USER_DATA` 指向的隔离目录运行，不对着本机的真实资料目录运行。

### 步骤 0　测量基线

在隔离资料目录里用受控服务跑一次长任务，包住 `store.save` 记录：调用次数（按调用来源分类）、每次序列化后的字节数、序列化、写入、fsync、改名各自的耗时、主文件大小随步数的变化、时间续约的次数和窗口被放大的情况、启动时读入主文件的耗时。同时记录每次落盘时业务部分（去掉将要搬走的字段之后）与上一次相比有没有变化，按调用来源汇总，得到上一节第一条所需的清单。受控服务的状态比真实资料小，再造一份放大的状态（多个功能、每个功能若干条命令回执）补测大文件下的耗时。真实资料目录不读；`%APPDATA%\Coprojer-dev\engineering-v1.json` 的大小请用户报一个数。结果放 `.runtime/harness-refactor/storage-baseline/`，摘要写回本文，在上面的推算之后加一段「实测」，推算原文留着对照。

负载、各段耗时的取法、来源的分类办法、汇总项和验收见 [存储搬迁步骤 0 设计](HARNESS_REFACTOR_STORAGE_STEP0_DESIGN.md)，执行交给 Codex，两者有出入时以它为准。这一步只加测量脚本，不改 `src/`，不依赖 ADR 0007 的接受与否。

判据：有了实测数字之后复核第 2 项的分级和「仍待处理」里的时间续约，再决定后面各步的细节。

### 步骤 1　日志读写器与落盘接缝

新增单文件模块（按拆分计划的硬约束，新模块必须是单个 `.ts` 文件）：追加一行并按等级决定是否 fsync、读回并容忍不完整的末行、正文的写入与读回校验。先不接线，用源码类脚本单测。

同时定落盘接缝。现在有 21 个脚本和夹具通过替换 `store.save` 注入失败、停止或崩溃（其中 15 个挂在 `package.json` 的命令里），例如 `scripts/fixtures/context-runtime-crash-host.cjs` 第 26–30 行在 `save` 返回后按回执状态退出进程。回执改走日志后这些替换点不再被触发。拟定的做法是让主文件保存、日志追加、检查点替换都经过 `store` 上同一个可替换的方法，脚本改为替换它。按拆分计划的约定，搬出去的代码不得提前捕获这个方法的引用。

### 步骤 2　回执台账与正文外置

`featureReceiptLedger` 的宿主改为追加回执行，`ReceiptHost` 的接口从「保存整份台账」改成「追加一条回执」（没有脚本直接使用 `ReceiptLedger`，按 grep 是 0 个）。接上正文外置。补 `execution-recovery.ts` 第 81 行的幂等判断，按上一节的顺序改 `applyReceiptProjection`。

### 步骤 3　检查点分文件

`saveCheckpoint` 改写 `checkpoint.json`；处理四处删除的先后和残留文件的识别。`store.ts` 第 62 行在启动时按「有没有检查点」决定是否升级智能体指令，这个判断要改成读新位置，结果必须与今天相同，否则已暂停任务的指纹会变。

### 步骤 4　额度、请求与用量、压缩、操作、活动事件

逐类改走日志，内存里的对象和上限不变。`RuntimeBudgetLease` 经 `budgetHost(owner, save)` 落盘（`runtime-budget.ts` 第 50 行），换掉传入的 `save` 即可；同一时刻只认一个预占的检查（第 76 行）不动。活动事件按有没有功能归属分别进功能日志和项目日志（62 处 `store.event(` 里 44 处带功能，18 处不带）。按步骤 0 的清单给靠捎带提交业务状态的调用点补显式保存。

### 步骤 5　交接与原件

按「仍待处理」里定下的提交点改 `prepareRuntimeHandoff`。`runtimeOriginals` 拟定为每次交接写一个独立文件，写一次、不再改。

### 步骤 6　搬迁与启动重放

启动时没有 `engineering-v2.json` 而有 `engineering-v1.json`：读 v1（沿用第 53–58 行的格式校验），按功能写出日志、检查点和正文，最后用「临时文件、fsync、改名」写出 `engineering-v2.json`。v2 主文件是提交标记：它不存在就说明搬迁没有完成，下次启动清掉 `engineering-runs/` 里的半成品重新做。全程不写 `engineering-v1.json`。搬迁不改检查点的任何字段，回执逐条过一遍 `validateReceiptRecord`，校验不过的保留原样并停下，不丢弃。已验收功能的运行记录直接写成封存状态。

启动重放：读 v2 主文件，再读每个未封存功能的日志和检查点，还原到 `store.data` 原来的位置。重放后 `state()` 给界面的内容与搬迁前逐字段相同（`snapshot()` 现有的四个运行时字段照旧不外传，`store.ts` 第 220–221 行）。

### 步骤 7　封存与提示

最终验收（`service.ts` 第 2407 行）时写摘要行并封存。这里的「封存」指日志停止写入、不再加载，与 `DOMAIN.md`「工具执行管线」词条里的「封存结果」不是一回事；要不要换一个词，2026-11-11 接受 ADR 0007 时没有讨论，仍待用户定，在那之前沿用「封存」。摘要的内容：请求数、工具调用数、用量合计、活动时间、回执计数、命令证据索引。用量里未知的项在摘要里仍记为未知，不按零合计。封存之后这个功能的日志不再加载。摘要拟定同时写进主文件里的功能记录，否则界面在已验收功能上没有东西可显示（「日志」页读的是 `feature.contextRuntime`、`feature.runtimeBudget` 和 `project.events`，`EngineeringPage.tsx` 第 2158–2160 行）。`service.ts` 里没有找到把 `done` 改回其他阶段的代码（启动开发要求阶段是 `ready` 或 `blocked`，退回要求是 `acceptance`），封存因此不需要「解封」。资料目录的占用超过阈值时在界面提示，清理由用户手动触发，只能清已封存功能的日志和正文。阈值和提示的位置没有定。

### 脚本

随各步一起改，不单独成步：34 个脚本和夹具含 `engineering-v1.json`，37 个引用 `executionCheckpoints` 或 `receiptJournals`，21 个替换 `store.save`。读 `store.data` 的断言因第 5 项不用改；从磁盘读 `engineering-v1.json` 再断言回执或检查点的要改路径和读法，崩溃注入的两组（`context-runtime-crashes`、`context-runtime-command-crashes`）在其中。拆分计划要建的等价脚本会记录 `store.save()` 的次数，这个基准在本阶段按设计会变，要随步骤重建并在提交说明里写明原因。

## 约束对照

| 产品约束 | 本计划里的落点 |
| --- | --- |
| 旧版本持久化数据要能打开 | 步骤 6：从 v1 搬迁，v1 不改写 |
| 已完成的功能记录、验证证据和最终验收结果不得丢失或被改写 | 这些内容留在主文件，搬迁时逐字带到 v2；步骤 7 只在最终验收时追加一条摘要 |
| 不得改掉已暂停任务的检查点指纹 | 步骤 3、6 不改检查点字段；`store.ts` 第 62 行的判断结果保持不变。本计划不依赖 ADR 0005 为一次性迁移所做的放宽 |
| 用量未知就保持未知 | 第二级记录丢失后不补零、不反推；步骤 7 的摘要保留未知 |

| 三个人工确认节点、开发与验证分离 | 不涉及 |

## 仍待处理

- **活动时间续约。** 按第 2 项，额度预占逐条 fsync，时间续约因此是约每秒一次带 fsync 的小追加，60 分钟的任务最多约 3600 次。把窗口放宽到 5 秒是 720 次，10 秒是 360 次；代价是崩溃时多扣最多一个窗口的时间，因为崩溃的预占不退还（`runtime-budget.ts` 第 129 行的注释）。要不要放宽、放到多少，等步骤 0 的实测再定。
- **第二级记录用于判断的一处。** `legacyReviewPause`（`service.ts` 第 1511–1519 行，第 2121 行调用）在没有检查点时靠活动事件判断旧任务是否停在验证阶段。ADR 0007 第二项要求恢复时读的内容都属于第一级，这一处与之不符。它只服务旧版本留下的数据，是把相关事件提到第一级，还是在搬迁时把判断结果固化下来，没有定。
- **第二级记录追加失败。** 今天请求记录或事件落盘失败会抛错并停下。改为只追加之后，失败是继续运行并把这段用量记为未知，还是照旧停下，没有定。
- **项目级和会话级的运行记录。** `contextRuntime` 和 `runtimeBudget` 在项目上也有（`src/shared/engineering.ts` 第 361–362 行），需求讨论、方案规划和通用助手经 `contextSession` 落盘，快照存在 `contextSnapshots`。七项决定只说了功能。在定下来之前，这几条路径继续走主文件的全量保存。
- **交接的提交点。** 见「一次落盘提交多样东西的地方」。
- **`result.output` 是否外置。** 读文件类工具的输出在结果行和 applied 行各出现一次，第 7 项没有点名它。
- **降级之后再升级。** v1 里新增的进度和已有的 v2 以谁为准，没有定；ADR 0007 末段同样列着这一条。
- **启动重放的耗时**没有测，并入步骤 0。
- **界面每 250 ms 轮询 `state()`**（`EngineeringPage.tsx` 第 252 行）会把整份可见状态深拷贝一遍，与落盘无关，本计划不处理；是否另开议题，用户还没有表态。
