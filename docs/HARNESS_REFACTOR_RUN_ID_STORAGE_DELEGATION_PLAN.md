## 已定的四项决定

| ADR 0007 | 议题 | 决定 |
| --- | --- | --- |
| 第五项 | 运行标识的生命周期 | 一次运行一个标识，跨暂停续接和交接不变；层级是范围、运行、步、模型请求与工具调用，不设「回合」层 |
| 第六项 | 运行标识的落地时机 | 拆分之后、存储搬迁之前；以可选字段加进现有 JSON；旧记录不回填 |
| 第七项 | 子运行能做什么 | 第一版只读调查，不能写文件，不能运行命令 |
| 第八项 | 委派在哪里开放 | 只在自由编码入口；固定交付工作流的工具集、工具合同版本和回执校验不动 |

四项都是用户在讨论里选的推荐项。没有采用的选项和理由写在 ADR 0007 里，这里不重复。

两个名字已经被占用。`runId` 指一次命令执行：`command-effects.ts` 79 行生成，证据记录带着它，界面 `CurrentEvidence.tsx` 13 行按它查。`turnId` 指需求讨论里的一次发言：`requirements.ts` 235 行生成，370 行拼进逻辑调用 id。运行标识不能用这两个名字。

### 范围键

运行标识的上一层是范围。现有的范围键有三种写法：

| 数据 | 位置 | 键 |
| --- | --- | --- |
| 检查点、回执表、交接前原件 | 主文件的 `executionCheckpoints`、`receiptJournals`、`runtimeOriginals` | `executionKey(projectId, featureId)`（`execution.ts` 78） |
| 规划、讨论、助手的快照 | 主文件的 `contextSnapshots` | `JSON.stringify([projectId, scopeId, role])`（`context-session.ts` 38） |
| 上下文归档、命令持久记录 | `engineering-artifacts/`、`engineering-commands/` 下的目录 | `sha256([projectId, featureId])`（`execution-artifacts.ts` 34，`command-effects.ts` 63） |

`contextSession` 三类调用方传的范围各不相同：方案规划是功能 id 或字面量 `'planning'`（`planning.ts` 20），需求讨论是 `'discussion:' + 参与者哈希`（`requirements.ts` 237），助手是项目 `'assistant'` 加会话 id（`general-assistant.ts` 153）。回执恢复要求 `receipt.scopeId === feature.id`（`execution-recovery.ts` 90）。自由编码的会话范围还不存在。

### 委派会碰到的固定点

- 回执校验写死了六个角色和各策略允许的工具（`receipt-ledger.ts` 45、57–58），子运行的角色和委派工具都不在名单里。
- 工具集固定 9 个，工具合同版本是 `engineering-tools-v3`（`tool-contract.ts`），加一个工具就要升版本。
- 累计额度同一时刻只认一个活动预占（`runtime-budget.ts` 76），并行的子运行没有地方记自己的活动时间。
- 项目级作业互斥按 `jobs.has(project.id)` 判断（`service.ts` 699），子运行不能另开一个作业。
- 写文件和跑命令前必须读完已验收原型，进度记在父运行的闭包里（1872–1875）；子运行读了原型算不算父运行读过，没有规则。
- 上下文归档按功能设 128 MB 上限，子运行的归档记在谁名下没有规则。
- 每条记录都全量落盘，并行的子运行会把落盘次数成倍放大。

前五条由第八项「只在自由编码开放」绕开：固定交付工作流的名单、合同版本和原型前置都不动。第六条见 C2 的拟定默认值，第七条由存储搬迁解决。

#### A1　命名

| 用途 | 拟定名字 | 说明 |
| --- | --- | --- |
| 运行标识（持久化字段） | `executionRunId` | 沿用现名，语义从「最近一条智能体快照的 id」改为「运行标识」 |
| 步号 | `stepId` | 沿用命令证据里的现有写法，字符串化的步数 |
| 父运行标识 | `parentExecutionRunId` | 只有子运行带 |
| 发起委派的工具调用 | `parentCallId` | 取父运行那次调用的逻辑调用 id |
| 代码里传递用的类型 | `RunRef` | `{ executionRunId; parentExecutionRunId?; parentCallId? }`，放在 `shared/` 下 |

沿用 `executionRunId` 的理由：证据记录、验证结果、证据投影和命令回执已经用这个名字存运行标识，界面不用改字段名；没有回归脚本引用这个名字。代价是规划、讨论、助手的运行也用带 execution 的名字，字面不贴切。备选是另起 `agentRunId`，缺点是容易和 `agentRuns` 快照自己的 `id` 混。这一项已于 2026-11-11 确认（执行说明第 10 节 A5）。存储搬迁计划的日志信封取用这里的 `executionRunId` 和 `stepId`。

#### A2　标识写进检查点，续接时读回

- `service.ts` 1544 行改为：有可续接的检查点就取检查点里的 `executionRunId`，否则新生成一个。不再取 `agentRuns.at(-1)?.id`。
- 1638 行写检查点时带上 `executionRunId`。`assertSupportedCheckpoint`（`checkpoint-version.ts`）只校验指定字段，不拒绝多出来的字段；`executionFingerprint`（1497–1510）的输入里没有运行标识。两条都是读代码得出的。
- 智能体快照加可选的 `executionRunId`，同一次运行续接几次就有几条快照指向同一个标识。快照自己的 `id` 不变，界面 `ContextWorkspace.tsx` 266–268 照旧显示最近 6 条。
- `contextSession` 的快照同样加可选字段，由 `context-session.ts` 52–65 的 `records.save` 包装写入，`runtime.ts` 不知道这个字段。`compatibleSnapshot`（`context-continuity.ts` 36–41）只看版本、身份和基线。
- 需求讨论不经过 `runRuntime`。一个参与者的快照跨多次发言保留历史，按 ADR 0007 对运行的定义，它的一次运行是这份快照从建立到失效的整段；`turnId` 照旧标识单次发言。这样界定的话一次运行会跨很多次发言，按运行汇总用量意义不大。执行说明 6.8 改为「一次发言一次运行，同一次发言中断后续接算同一次」，本条原先的界定列为备选。2026-11-11 用户确认采用前者（执行说明第 10 节 A4），ADR 0007 第五项的文字已随之改写；本条开头按快照寿命的界定不再适用。

没有运行标识的旧暂停检查点续接时怎样补发，ADR 0007 原先列为未确定。两个做法：续接时新生成一个，下次保存检查点时写入；或者沿用当时最后一条快照的 id。前者简单，但这次运行在续接前留下的证据记录带的是旧号，两段对不上；后者能对上最后一段，但快照可能已被 200 条的上限挤掉。执行说明 6.4 用前者，后者和「取最后一条命令证据的标识」列为备选；2026-11-11 用户确认用前者（执行说明第 10 节 A2）。

#### A4　请求记录与流量记录互指

工作包A3已将新请求记录的ID记到工程运行对象，流量取值仍待工作包A7，尚未接通。

同一次模型请求现在有三个号：请求记录的 `id`、流量记录的 `id`、供应商的 `responseId`。拟定做法是请求记录生成之后把它的 `id` 放到运行对象上，流量记录开始时读到并存成可选的 `requestId`。一次运行同一时刻只发一个推理请求；计数和压缩请求走操作记录，对应操作记录的 `id`。传法见执行说明 6.9：连接上加一个可选的取值函数，`traffic.start` 多收一个可选参数，只做流量指向请求这一个方向。写流量记录失败照旧只丢统计，不影响请求。

运行标识跨续接不变之后，下面几处读 `executionRunId` 的地方看到的值会变，改 1544 行之前先用特征测试锁住现有行为。完整的清单（另有 1751、1788、1882、1928、1963、2256 行）在执行说明 6.4。

#### A6　完成判据

- 从一条失败的验证结果出发，能找到命令和源码指纹、所属的运行、那一步的模型请求和流量记录里的用量；用量未知的仍显示未知。
- 暂停再续接、交接换模型之后，新旧两段的记录带同一个运行标识。

- 旧数据能打开，旧记录上没有新字段时界面不报错。

第一条在存储搬迁之前有一个限度：请求记录只留最近 200 条、活动事件 1200 条、智能体快照 200 条，被挤掉的记录查不到。按运行查全量要等日志落地。

### B　存储搬迁：与本文相接的部分

存储搬迁的决定、布局和步骤见 [存储搬迁计划](HARNESS_REFACTOR_STORAGE_PLAN.md)，这里只列三处衔接。

- **信封字段。** 日志信封里的运行标识和步号用 A1 的 `executionRunId`、`stepId`，子运行的行另带 `parentExecutionRunId`、`parentCallId`。A 部分先把这些字段以可选形式加进现有 JSON，搬迁时信封直接取用；A 落地之前产生的记录搬进日志时这两个字段为空。
- **封存之后的查询。** ADR 0007 第十项规定最终验收之后日志封存、不再加载。A6 第一条「从失败的验证结果找到模型请求」在已封存的功能上要按需读封存的日志，这条读取通道两份计划都没有设计；执行说明第 8 节有一条建议（只读的分页读取函数），没有写进存储搬迁计划。
- **分级的旁证。** 存储搬迁计划把压缩记录、操作记录和请求记录归在只追加一级。我按字段名搜了 `src/main`、`src/shared`、`src/renderer/src`：压缩记录和操作记录只在续接、交接时整表带过去（`service.ts` 1554–1556、599）并在界面显示（`ContextDetails.tsx` 43–44）；`responseId` 只有两处写入（`service.ts` 1814，`context-session.ts` 77），没有读取方；请求记录在循环里只被「取最后一条、按哈希对上就更新」（1807、1819）。没有找到按它们作流程判断的地方，与那份计划的分级一致。搜索没有运行验证。

并行的子运行要等存储搬迁之后再放开，理由见「委派会碰到的固定点」最后一条。存储搬迁计划的约束对照里写着「每个功能日志同一时刻只有一个写入者」，并发的子运行往同一份日志里写时这一条怎样成立，见「仍待处理」。

### C　只读委派

前提：自由编码入口已经做完（规则、审批、通用 shell 之后）；A 部分完成。并行还要等存储搬迁。

#### C1　工具形态

委派是工具执行管线里的一个工具，只登记在自由编码入口的工具集里，固定交付工作流的 9 个工具和合同版本不动。父运行的模型调用它，参数是一段任务说明；任务事实由父运行写进参数，子运行看不到父运行的历史。

宿主收到调用后新建一次 `runRuntime`：空历史，工具只有 `list_files`、`read_file`、`read_file_lines`、`search_files`、`read_context`，自己的步数上限，记录带 `parentExecutionRunId` 和 `parentCallId`。它在前台运行，父运行等它返回。子运行的工具集里没有委派工具，所以不能再委派。结论作为这次工具调用的结果回到父运行。

规则对子运行照样生效：deny 拒绝，allow 放行，命中 ask 时不弹卡片，直接拒绝并把原因写进结果。父会话里逐次作出的审批不继承。自由编码里读项目目录内的文件如果默认是 ask，子运行什么也读不了；这取决于 ADR 0005 还没定的规则设计。

#### C2　拟定的默认值

下表全部是拟定，待确认。取值是比照现有常量定的，没有实测依据。

| 项 | 拟定值 | 比照 |
| --- | --- | --- |
| 子运行步数上限 | 12 | 验证准备的 `preparationStepLimit` |
| 结论内联长度 | 6000 字符，超出部分归档，父运行用 `read_context` 分页重读 | `context.ts` 的 `PAGE_SIZE` |
| 并发 | 1；存储搬迁完成后再考虑 2 或 4 | 只读并行的 1 / 2 / 4 |
| 模型 | 沿用父运行的连接 | — |
| 额度 | 子运行的请求和工具调用记在父运行的预占上；子运行的步数不计入父运行的步数上限 | 累计额度只认一个活动预占 |
| 崩溃或中断 | 不自动重跑，结果写「子运行中断」，由父运行决定是否再委派 | 一次子运行最多 12 步，重跑代价不小 |
| 已验收原型的必读进度 | 子运行读了不算父运行读过 | 自由编码没有这条前置，写明以免日后接进固定交付工作流时混淆 |
| `read_skill` | 不给子运行 | — |
| 归档配额 | 记在父运行的范围名下 | 现有每功能 128 MB |

#### C3　完成判据

- 子运行的工具集里没有写文件、运行命令和委派工具，由代码里的工具集保证，不靠提示词。
- 子运行的每条记录都能沿 `parentCallId` 找到父运行的那次工具调用。
- 子运行的结论不产生验证证据，不改变任何功能的验证状态。
- 父运行被取消时子运行随之停止；子运行出错不让父运行失败。

## 约束对照

存储一侧的约束对照见存储搬迁计划，这里只列运行标识和委派。

| 产品约束 | 本计划里的落点 |
| --- | --- |
| 三个人工确认节点 | 不涉及。委派不进固定交付工作流 |
| 一个时段只推进一项功能，项目级作业互斥 | 子运行在父运行的作业内执行，不另占作业 |
| 开发与验证职责分离 | 开发智能体和验证智能体不能委派（第八项） |
| 模型声称完成不算证据 | 子运行的结论只是调查资料，C3 第三条 |
| 用量未知就保持未知 | 旧记录缺运行字段显示未知，不回填（A3） |
| 监控失败不影响推理 | 流量记录只多带字段，写失败仍只丢统计（A4） |
| 旧数据要能打开 | 新字段全部可选（A3） |
| 不得改掉已暂停任务的检查点指纹 | 指纹输入里没有运行标识（A2）。只读了代码，A6 第三条用来验证 |
| 结果不确定时停下而不是重放 | 回执上的新字段不参与恢复判断（A3）；子运行中断不自动重跑（C2） |
