# 运行记录改为追加式日志并带统一的运行标识，子智能体委派先只在自由编码里做只读调查

工程状态现在全部放在用户资料目录的单个 `engineering-v1.json` 里，每次 `save()` 把整份数据序列化、fsync、原子改名。回执、请求与用量、压缩记录、活动事件、额度预占的每一次变化都走这条路，`src/main` 里直接调用 `store.save()` 的地方有 64 处；按代码路径估计，记回执的运行每一步约有 15 次全量落盘，这个数没有实测。各类运行记录用的标识互不相通：智能体快照的 id 被当作运行标识，但暂停后每续接一次就换一个，快照又只保留最近 200 条；同一次模型请求在请求记录、流量记录和供应商响应里各有一个号，流量记录里没有项目、功能或运行字段；活动事件只带功能和种类，其余信息都在自由文本里。[ADR 0005](./0005-tool-pipeline-and-free-coding-entry.md) 决定自由编码入口包含子智能体委派，同时把「子智能体委派的形态」和「存储改为追加式、统一的运行关联标识」列为未确定事项。2026-11-11，用户在三轮讨论中就这三件事做了十一项选择，本 ADR 记录这些选择和它们之间的约束。三件事写在同一份 ADR 里，是因为它们互相牵制：日志的每一行要带运行标识才能按运行查询；子运行要靠父运行的标识挂到发起它的那次工具调用上；并行的子运行在全量落盘的存储上放不开。现状的源码位置、实施步骤和拟定的默认值见 [运行标识、存储搬迁与只读委派计划](../HARNESS_REFACTOR_RUN_ID_STORAGE_DELEGATION_PLAN.md)。存储部分的现状、落盘布局和实施步骤另见 [存储搬迁计划](../HARNESS_REFACTOR_STORAGE_PLAN.md)；第九至第十一项定在前八项成文之后，两份计划在存储上有出入时以存储搬迁计划为准。

第一，运行记录从主文件搬出，改为每个功能一份追加式日志。回执、请求与用量、压缩记录、活动事件、额度预占写进按行追加的 JSONL 日志；检查点单独存成一个小文件，整份替换；项目、功能需求、功能记录、验证证据和最终验收结果这些业务状态留在主文件，继续用现有的「写临时文件、fsync、改名」方式保存。讨论时摆出的另外三种形态没有采用。只拆文件、不追加：每次变化仍要重写所在的整份文件。`save()` 的接口不变、底下改成预写日志：调用点和脚本都不用动，但数据仍是一整块，日志只是它的重放手段，不能按运行查询。完整的事件溯源：业务状态也改成由事件推导，改动面覆盖全部已完成的功能记录，超出这次要解决的问题。改用 SQLite 没有进入比较，因为 `node:sqlite` 在 Electron 44 里是否可用没有核实。

第二，落盘的可靠性分两级。回执的意图、结果和 applied 标记，累计额度的预占，检查点，这三类逐条 fsync，因为它们决定崩溃后能否对账、额度会不会被绕过。请求状态、用量、展示用的预算和活动事件只追加、不 fsync。后一类在崩溃时可能丢掉最近几条，丢了就按「用量未知就保持未知」处理：界面如实显示未知，不补零，不从别的记录反推。这条分级难以回退的地方在于恢复逻辑会依赖它：凡是恢复时要读的内容都必须属于第一级，实现时不得为了省一次 fsync 把它挪到第二级。

第三，搬迁写新文件，不改旧文件。新版本第一次启动时读取 `engineering-v1.json`，写出 `engineering-v2.json` 和日志目录，之后只读写新位置；`engineering-v1.json` 原样留作备份。代价是降级：旧版本只认 `engineering-v1.json`，降级后看到的是搬迁那一刻的状态，搬迁之后的进度在旧版本里看不到。用户接受这一点。读 `engineering-v1.json` 的回归脚本要跟着改路径。搬迁本身不改检查点里的指纹字段，按对源码的核对，暂停中的任务可以原样带到新位置，所以这一步不依赖 ADR 0005 为一次性迁移所做的放宽；它是否与那次迁移合成同一个版本发布，由迁移阶段的计划决定。

第四，存储搬迁排在拆分之后的迁移阶段，日志的信封与运行标识一起设计。信封指每一行日志都带的公共字段，包括范围、运行标识、步号、记录种类和时间。开工前先在隔离资料目录里测出现有实现的 `save()` 次数、每次写入的字节数和耗时，写进计划当基线；没有这组数字，搬迁之后无从判断改善了多少，也无从判断第二项的分级是否值得。

第五，一次运行只有一个运行标识，它跨暂停续接和交接保持不变。运行指一个智能体从接到一次交办开始、到完成或检查点失效为止的一段工作：工程执行和方案规划的运行从空历史开始；需求讨论和通用助手的历史跨发言累积，一次发言、一条用户消息各是一次运行。中途暂停、取消或出错之后，只要续接的是同一个检查点，就仍是同一次运行，交接换了模型也一样。运行标识写进检查点，续接时从检查点读回，不再取智能体快照的 id。标识的层级是：范围（项目加功能，或会话）之下是运行，运行之下是步，步之下是模型请求和工具调用；子运行另带父运行的标识和发起它的那次工具调用的标识。不设「回合」这一层：固定交付工作流里一次运行只有一个输入，自由编码里每条用户消息就是一次运行，多出一层没有东西可放。角色和模型是运行的属性，不充当标识。现有的清单 id 继续标识配置的代次，交接时照旧换新；工具调用继续用现有的调用组 id 和逻辑调用 id。讨论中把运行标识简称为 `runId`，而现有代码里 `runId` 已经指一次命令执行，持久化字段因此不能直接叫这个名字，具体命名见计划。没有采用「每段一个号，再用指针串起来」，那样查一次完整运行要沿链回溯，交接点上容易断；也没有采用「沿用快照 id，只给流量和事件补字段」，那样续接换号的问题留着，快照超过 200 条之后引用会悬空。

第六，运行标识在拆分之后、存储搬迁之前落地。拆分阶段会把 `agentLoop` 的闭包状态收成一个显式的运行对象，运行标识由它承载；各类记录先以可选字段的形式加进现有的 JSON，存储搬迁时日志信封直接取用。旧记录不回填，字段缺失就是未知。这一步不得改掉已暂停任务的检查点指纹，对照源码核对的结果是可以做到：检查点指纹的输入里没有运行标识；检查点的版本校验只看指定字段，不拒绝多出来的字段；回执的意图哈希只覆盖一张固定的字段表，表外加字段不影响旧回执的校验。这次核对只读了代码，没有运行。最后一点同时是一个限制：新加的字段不受意图哈希保护，只能用来关联和查询，恢复逻辑不得依据它作判断。没有采用「与存储搬迁同一批改」，两件事叠在一起出问题时难以定位；也没有采用「拆分之前先做」，那要在约 470 行的内联闭包里加传参，拆分时还得再搬一次。

第七，子智能体委派的第一版只做只读调查。子运行只拿到读文件、搜索和读上下文这几个工具，不能写文件，不能运行命令。这回答了 ADR 0005 留下的「子智能体能否写文件」：第一版不能。这样做不涉及写冲突、文件副作用的回执和审批卡片，仓库内的两份研究也都建议从只读并行起步；收益限于隔离上下文和并行阅读。没有采用「可写、串行」，那要给子运行接上文件回执、审批和崩溃对账，父运行已读内容的版本也会过期；也没有采用「可写、并行、各自隔离」，现有的路径规则拒绝 `.git`，仓库里没有任何 git 集成，合并之后怎样验收也没有设计。

第八，委派只在自由编码入口开放。固定交付工作流的工具集、工具合同版本和回执校验都不动，开发智能体和验证智能体不能委派。代价是委派要等自由编码入口做完才能用，排在规则、审批和通用 shell 之后。没有采用「开发智能体也能委派」，那要改回执校验里写死的角色和工具名单、升工具合同版本，并处理已验收原型的必读进度归谁；也没有采用「开发和验证都开放」，那还要先论证子运行的结论不会削弱验证的独立性。

委派的下列形态是随上述选项一并提出的，用户没有逐条表态，本 ADR 记为拟定。2026-11-11 接受本 ADR 时没有逐条确认，它们仍是拟定，写只读委派的实施计划时再确认或修改。委派是工具执行管线里的一个工具，由父运行的模型调用。子运行从空历史开始，任务事实由父运行写进委派的参数。它在前台运行，一次性返回，父运行等它结束；子运行不能再委派。结论作为这次工具调用的结果回到父运行，只是调查资料。deny 和 allow 规则对子运行同样生效，命中 ask 时不弹审批卡片，直接拒绝并把原因回报给父运行；父会话里逐次作出的审批结果不继承。步数上限、结论长度、并发数、模型、额度记账、崩溃后的处理这些取值都列在计划里，同样是拟定。

第九，搬进日志的内容不再写进主文件，变更登记留在主文件。累计额度、活动事件，以及上下文运行状态里的请求、压缩、操作和回执视图，落盘时只进日志；启动时从日志重放到内存里原来的位置，内存中的数据形状不变，界面读到的状态和直接读内存数据的回归脚本因此不用改。变更登记按功能和路径各存一条，不随调用次数增长；界面的「代码变化」页要展示它的前后全文，验证准备要拿它与磁盘内容比对，所以它留在主文件。这回答了第一项留下的范围问题。没有采用「主文件里留一份定期快照」，同一份数据存两处，崩溃后两处不一致时没有判据说明以谁为准；也没有采用「变更登记也外置」，那要加一条读取通道并改界面，验证准备的比对也得改成读外置的正文。这一项带来一条实现上的约束：现在任何一次保存都会把内存里尚未落盘的业务改动一并提交，活动事件、回执和额度改走日志之后这种捎带不再发生，原来靠它落盘的业务状态要改成显式保存；回执投影和交接这两处在一次保存里提交多样内容，拆成多个文件后要重新规定提交的先后，并保证崩溃后重做不会产生重复条目。

第十，日志在功能进行中不删、不折叠，最终验收之后封存。封存时写一条摘要，记请求数、工具调用数、用量合计、活动时间、回执计数和命令证据的索引；用量里未知的项在摘要里仍是未知，不按零合计。封存之后这个功能的日志不再加载，也不自动删除；资料目录的占用超过阈值时界面提示，由用户手动清理。内存里的投影沿用现有上限：活动事件 1200 条、请求 200 条、压缩 64 条、操作 100 条。没有采用「按大小分段滚动」，那要规定检查点覆盖到日志的哪一行，而终结回执在功能完成之前都可能被对账读到，不能随旧段删除；也没有采用「沿用现有上限、超出就重写文件」，那样日志不再是纯追加，截断还会丢掉用量合计。这一项难以回退的地方在于封存之后的记录不再参与任何恢复判断：功能一旦最终验收，它的回执只是历史资料。

第十一，回执里的正文在落盘层去重，不换回执的合同版本。写日志行时，把文件写入前后的内容、调用参数里的文件内容、命令前后的工程快照正文和命令造成的变更正文换成 sha256 引用，正文按哈希各存一份；读回时按引用还原并复算哈希，正文缺失或哈希不符时这条回执按不可核对处理，停下等待核对，这延续了「结果不确定时停下而不是重放」。内存里的回执对象、意图哈希、结果哈希、各项校验和回执的合同版本都不变。能这样做的依据是两个哈希都是对内存里的对象算的，落盘时怎样编码不在哈希的覆盖范围之内；这一点只读了代码，没有运行。正文必须先于引用它的日志行落盘。外置的是今天已经写进主文件的同一份内容，脱敏仍在形成回执时完成，不引入新的落盘路径。没有采用「不去重、只靠增量行」，每条命令回执仍要追加前后两份工程快照，按对验收样例的只读实测一份约 0.15 MB；也没有采用「换回执的合同版本、回执里不存正文」，那要改意图哈希的字段表、文件回执与命令回执的校验和检查点的版本白名单，两套校验长期并存，存储格式也就和工具合同版本绑在了一起。

本决策不改变三个人工确认节点，也不改变开发与验证的职责分离：委派不进入固定交付工作流，子运行的结论与自由编码的其他输出一样不产生验收证据，不能把功能需求标记为已验证或已验收；这与「模型声称完成不算证据」是同一条约束。它不改变 [ADR 0003](./0003-serial-feature-development.md)：子运行在父运行的作业之内执行，不另占一个项目级作业。「用量未知就保持未知」由第二项落实；「监控失败不影响推理」不变，流量记录只是多带几个字段，写不进去仍然只丢统计。「旧版本持久化数据要能打开」由第三项和第六项落实：搬迁保留旧文件，新字段一律可选。「已完成的功能记录、验证证据和最终验收结果不得丢失或被改写」不变，这些内容留在主文件，搬迁时逐字带过去。本 ADR 细化了 ADR 0005 第五项里的子智能体委派，不改变它的其他内容；与 [ADR 0006](./0006-stable-prompt-prefix-and-working-window.md) 没有冲突，子运行使用同一套提示词分区和工作窗口。「运行」「委派」「子运行」三个词条已在本 ADR 被接受时补进 `docs/architecture/DOMAIN.md`；后两条只写了第七、第八项已定的内容，上一段仍是拟定的形态没有写进词条。

以下事项尚未确定：活动时间的预占按第二项要逐条 fsync，而它现在约每秒续约一次，续约的间隔要不要放宽，等开工前的实测再定；旧版本留下的暂停任务在没有检查点时靠活动事件判断是否停在验证阶段，活动事件属于第二级，这与第二项「恢复时要读的内容都属于第一级」不符，怎样处理没有定；第二级记录追加失败时是继续运行并把这段用量记为未知，还是照旧停下；交接在一次保存里同时写原件、检查点、台账和业务字段，拆成多个文件后的提交点没有设计；资料目录提示清理的阈值和界面形态；启动时重放未封存功能日志的耗时没有测；项目级的讨论、方案规划和助手会话的运行记录怎样归档，在定下来之前它们继续走主文件；降级之后再升级时，旧文件里新增的进度与已有的新文件以谁为准；自由编码里读取项目目录内的文件是否默认允许，这决定了「命中 ask 就拒绝」的子运行能不能工作，它取决于 ADR 0005 尚未确定的规则设计；自由编码会话是否绑定项目、是否与固定交付工作流共用项目级作业互斥，仍如 ADR 0005 所列。本 ADR 于 2026-11-11 被用户接受。同时确认的是运行标识的十项实现取值，列在 [交给 Codex 的执行说明](../HARNESS_REFACTOR_CODEX_HANDOFF.md) 第 10 节 A 组，其中包括原先列在这里的一条：没有运行标识的旧暂停检查点，续接时新生成一个标识，下一次保存检查点时写入，旧证据里已有的值不改写。存储一侧的待定项（同节 S 组）、委派的形态与默认值（同节 C 组）没有随之确认。接受不代表这些改动已在当前代码中实现。
