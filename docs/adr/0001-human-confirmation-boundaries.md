# 产品工程流程保留三个人工确认节点

个人开发者需要掌握需求范围、实现方向和交付结果，同时将中间的执行组织交给系统。用户已确认：Coprojer 产品内的工程流程保留「需求确认」「方案确认」「最终验收」三个节点，分别确认范围与验收标准、实现方式与任务拆分、实际交付成果。

在这些节点之间，系统组织上下文准备、任务派发、代码实现、自动检查和记录更新。此选择在自主推进与人工掌握关键决策之间划定边界：不要求人逐条驱动执行，也不让智能体自行决定业务成果已经被接受。测试通过和最终验收通过分别记录，最终验收结果由开发者作出。

用户进一步确认：三个节点以一项可独立验收的「功能需求」为单位。所属「实现任务」由系统在已确认范围内组织推进，不逐个重复三次确认；任务结果汇总到功能需求统一验收。这样既能掌握功能级进度，也避免细碎任务确认打断自动执行。

用户随后拒绝了一个额外确认场景：执行 Excel 导出时发现需调整多个模块共用的权限规则，不要求先提交变更说明并等待确认。该场景允许继续执行，保留原来的三个确认节点，不增加执行中的人工变更关。

用户进一步明确自主调整的约束：智能体可以改变实现方式，但不能自行删改已确认的需求目标或验收标准。无法满足的验收项必须如实呈现为未达成，不能通过降低要求宣称完成。因此「方案确认」确认的是初始执行方向，允许后续实现路径在固定目标下演进；上述权限规则调整同样受这一约束。

验证失败的异常恢复也有明确边界：首次验证失败后，默认最多自动进行 3 轮「开发修复＋验证复查」。仍未通过时暂停该功能，保留代码与记录、展示未解决问题及尝试结果，由开发者决定继续尝试、更换智能体或自行处理。这是自动修复超限后的异常处理，不增加正常交付流程的人工确认节点，也不允许通过降低验收标准宣称完成。

模型调用与环境故障、执行中断、其他范围变化、合并和发布时如何处理，仍需后续讨论；本决策不把上述回答扩大为所有行为均可自主决定，也不确定执行引擎或数据存储技术。
