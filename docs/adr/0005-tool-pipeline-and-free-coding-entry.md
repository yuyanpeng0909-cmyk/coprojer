# 统一工具执行管线，并新增受审批约束的自由编码入口

工程工具的执行目前内联在 `EngineeringService.agentLoop` 里：角色工具裁剪、任务修订号复核、已验收原型的必读前置、密钥拒绝、预算占用、回执记录和命令证据登记，都是同一个闭包里的语句，权限全部硬编码。方案规划另有一份内联的执行逻辑，需求讨论与圆桌会议则自己手写循环。[ADR 0004](./0004-coprojer-owned-agent-execution.md) 确定由 Coprojer 自己组织工具执行时写明「工具权限细节尚未确定」。2026-11-11，用户在两轮讨论中就 harness 重构做了八项选择，本 ADR 记录这些选择、它们之间的约束，以及与已有 ADR 的关系。

第一，重构从工具执行管线入手。工程工具的每次调用都经过同一条固定阶段的管线，阶段之间留具名 hook 点，权限判定和 hook 都挂在这条管线上。用户选定的阶段顺序是「校验参数 → 权限判定 → 前置 hook → 执行 → 后置 hook → 记录」。对照现有源码后，本 ADR 把「记录」拆成两处并固定其位置：有副作用的调用必须在执行之前把意图写入回执台账，执行之后再封存结果。完整顺序因此是：校验参数、权限判定、准备副作用并记录意图、执行前复核权限并占用预算、前置 hook、执行、后置 hook、封存结果并更新功能记录。前置 hook 排在意图落盘之后，是现有代码的实际行为：原型必读前置的拒绝会被封存成一条失败回执。意图落盘之前另有一个只能拒绝的 hook 点，用于参数含密钥这类不允许写进台账的情形，在这里被拒的调用不产生回执。这个顺序决定了崩溃后能否对账，属于本决策的一部分，实现时不得调换。

第二，hook 第一版只供内部使用。hook 是 Coprojer 自己注册的 TypeScript 模块，用来承载现有的内联规则；不提供用户可配置的 hook，不执行外部脚本，也不读取项目目录里的 hook 配置。三个人工确认节点、开发与验证职责分离、源码指纹使旧验证失效这些产品约束继续落在代码里，不改写成提示词要求，也不改写成可被关闭的 hook。

第三，先整理结构再加能力。第一阶段只做不改变行为的拆分，靠现有 `scripts/` 回归脚本和新增的特征测试证明等价；规则引擎、审批、通用 shell 和新入口都排在拆分完成之后。拆分阶段的步骤见 [拆分阶段实施计划](../HARNESS_REFACTOR_SPLIT_PLAN.md)。

第四，数据兼容采用一次性迁移。新版本启动时把旧的持久化数据迁移一次；已完成的功能记录、验证证据和最终验收结果必须保留并能打开。迁移时处于暂停状态的旧任务，允许要求用户重新开始，不再保证其检查点可以续跑。迁移完成后可以删除按字符数计算的 `legacy` 上下文预算，以及为旧检查点版本保留的兼容分支。这修订了此前「已暂停任务的检查点指纹不能被升级逻辑改掉」的约束：该约束收窄为「已完成记录不得丢失或被改写」，`CLAUDE.md` 中的对应条目已同步修改。收窄只为一次性迁移服务；拆分阶段不改变行为，检查点指纹在那期间仍然不变。

第五，Coprojer 往通用编码智能体的方向扩展，新增一个与固定交付工作流并列的「自由编码」入口，包含子智能体委派。自由编码以对话方式直接读写代码和执行命令，与固定交付工作流共用同一套 runtime 和工具执行管线。它没有需求确认、方案确认和独立验证，因此不产生验收证据：自由编码中的任何输出都不能把功能需求标记为已验证或已验收，也不能删改已确认的目标和验收标准。自由编码改动源码后，现有的源码指纹机制照常使进行中功能的旧验证失效。[ADR 0001](./0001-human-confirmation-boundaries.md) 的三个人工确认节点只约束固定交付工作流，在那里保持不变；本 ADR 不取代 ADR 0001，也不取代 [ADR 0003](./0003-serial-feature-development.md)。

第六，自由编码入口提供通用 shell，由 allow / deny / ask 三类规则加逐次调用的审批卡片约束。没有规则命中时按 ask 处理；deny 优先于 allow；不提供跳过全部审批的模式。命令的进程树继续由 Windows Job Object 约束。Job Object 只管进程的存续，不限制文件访问和网络访问，Windows 上目前也没有可用的操作系统级沙箱，所以对项目目录之外的文件和对网络的访问，审批是唯一的防线。界面和文档必须照此如实说明，不得把规则加审批称为沙箱或隔离。本 ADR 不改变固定交付工作流中各执行角色的命令限制：开发智能体、验证智能体等角色仍只能运行 `npm` 与 `node` 加参数数组，不经 shell。

仓库内的两份研究都对开放 shell 持谨慎态度。Pi 架构研究把「直接开放 PI 全权限 bash 取代当前边界」列为不应该做的事；DeepSeek harness 研究提醒不要把 Windows 上的部分约束包装成完整隔离。本决策与这两条并不冲突，但前提必须写明：通用 shell 不取代现有边界，只出现在新入口里；它不是全权限的，每次调用都要过规则和审批；它也不被宣称为隔离。这三条里任何一条在实现中做不到，通用 shell 就不应发布。

本决策使 Coprojer 需要新增并长期维护权限规则、审批交互和第二个产品入口。它细化了 ADR 0004 中未确定的工具权限部分，但没有改变「由 Coprojer 直接调用模型并组织工具执行」这一前提。「自由编码」「工具执行管线」「审批」三个词条已随本 ADR 的接受补进 `docs/architecture/DOMAIN.md`。

以下事项尚未确定：自由编码会话是否必须绑定项目，是否与固定交付工作流共用项目级作业互斥；固定交付工作流的执行角色将来是否也能获得受审批约束的 shell；规则的存放位置与作用域（全局、项目或会话），以及审批卡片的界面形态；子智能体委派的形态，包括子智能体能否写文件、是否继承父会话的审批结果；一次性迁移是否同时移除 `runtimePolicy: 'legacy'` 这条不记回执的执行路径；存储改为追加式、统一的运行关联标识。上下文与压缩（模型摘要、工具结果清理、提示词缓存前缀、默认策略从 `legacy` 转为 `adaptive`）在本 ADR 起草时未定，已由 [ADR 0006](./0006-stable-prompt-prefix-and-working-window.md) 确定。本决策于 2026-11-11 被接受，不代表这些能力已在当前代码中实现。
