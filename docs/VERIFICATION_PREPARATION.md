# 自动补齐验证条件

Coprojer 在独立验证发现 `unverified` 后，先核对验证缺口，再执行可自动完成的准备工作并自动复验。准备不是业务开发，也不是验证通过。最终人工验收与功能串行顺序保持不变。

## 流程

1. 独立验证读取当前工程、运行已有检查，逐项记录 `passed / failed / unverified`。明确缺陷或实际断言失败进入原代码修复；缺少脚本、依赖、命令证据或运行条件保留未验证。
2. 只读诊断读取实际文件、已确认范围、主机平台、脚本和依赖安装状态。每项缺口记录判断依据、自动/外部/未知分类以及下一步；未知不自动写成“需要人工”。
3. 验证准备复用该功能的开发智能体，但采用独立执行角色、工具限制、预算和审计记录。混合缺口先处理可自动部分。
4. 准备有实际进展后，独立验证重新运行检查。即使准备只完成部分工作，也先复验已补齐部分，再展示剩余外部或技术阻塞。准备者的 `ready` 或文字总结不能标绿验收条件。
5. 只有独立验证支持全部条件通过，功能才进入“成果验收”；仍需用户明确验收才能推进执行计划。

界面在功能详情展示“分析验证缺口 / 准备验证条件 / 重新独立验证”。正常自动路径不用反复点击继续。暂停时展示剩余缺口、依据、最小外部输入，以及已完成的准备结果；保留“继续验证”入口。

## 自动处理范围

- 在 `tests/`、`test/`、`__tests__/`、`scripts/`、`fixtures/` 添加检查脚本和夹具，可添加测试配置。只允许修改本功能准备阶段创建、且没有被外部改动的测试资料。
- `package.json` 文件工具只允许添加 `test:*` 命令，保留原有命令及配置。已有脚本需修复时添加保留原标准的补充脚本；原断言不删除、不替换。
- 用受限 `npm install --save-dev --ignore-scripts <包>` 安装明确缺失的项目开发依赖；可以使用项目内 `tests/fixtures/` 的离线包。已有依赖不能借机升级，不修改生产依赖；安装生命周期脚本不自动运行。
- 构建、运行已有检查或新增检查。测试进程以项目为工作目录，命令最长 300 秒。每次命令提供独立 `COPROJER_TEST_USER_DATA` 和 `COPROJER_EVIDENCE_DIR`，检查脚本须使用隔离用户目录，并在 `finally` 关闭自己创建的应用和进程。
- 日志、截图、检查结果保存在 `.runtime/verification-evidence/<run-id>/`；临时用户目录和 npm 缓存位于 `.runtime/coprojer-checks/<run-id>/`，完成或取消后清理。应用崩溃时，进程生命期管道关闭会终止其测试进程；重启只清理由本系统登记且辅助进程已不存在的孤立目录，不根据旧 PID 杀进程。

验证角色仍不能写文件、安装依赖或执行内联 Node 代码；只读诊断不能运行命令。诊断阶段只读是职责限制，不代表独立验证也没有命令能力。允许执行 `test:tray:smoke` 这类多级 `test:*` 命令。准备阶段禁止写业务源码、覆盖原测试、改变已确认标准、全局安装、提权、付费及外部账号授权。准备命令结束后检查受保护文件，若发生越界改动则停止、保留现场和差异，不自动回滚用户文件，也不能形成通过结论。

这些是工程工具的边界及审计检查，并非操作系统级沙箱。npm 脚本及 Node 程序仍以本机用户权限运行；新增脚本必须遵守项目范围和数据隔离约束。

## 外部与技术阻塞

没有项目内脚本本身不是人工阻塞。缺少可安装的测试开发依赖，通常应先自动准备。确实缺少目标操作系统/设备、凭据、明确授权、真实桌面输入或人工观察能力时，保留 `unverified`，指出实际依据和最小需要补充的条件。

Windows 诊断会有界探测当前交互桌面、屏幕和本机 UIAutomation/Forms 是否可访问。探测成功仅表示可以尝试准备原生交互检查；不能据此标记桌面测试通过。旧文档中其他工具的坐标/截图错误不自动成为当前环境阻塞。准备脚本可以使用项目 Node 调用本机 PowerShell/.NET 和 Win32 输入，只操作本次启动的隔离应用与已定位的对应托盘；实际鼠标输入与菜单回调继续分开记录。

网络安装失败、准备模型连接失败、无进展、未知工具能力或准备预算耗尽，记录为技术阻塞，不统一归类为“必须人工”。同一源码、环境与缺口已尝试过的准备不会无变化重复。用户补齐条件后可继续验证，实际检查仍会重跑。

平台与测试时长来自目标项目最新已确认范围。不存在全局“只测 Windows”或“必须 25 分钟”规则。菜单回调或 Mock 不构成真实桌面鼠标输入；短时运行不构成长时精度测量。

## 预算、恢复与证据

- 原开发/验证维持每次 36 个工作回合和已有 3 轮代码修复上限。
- 准备独立最多 2 轮，每轮准备最多 12 个工作回合；每次只读诊断最多 6 回合，每回合最多 8 个工具调用。到达步骤上限最多追加一次无工具结论整理。准备不增加或重置 `repairRound`；反复点继续也不会重置准备预算。
- 每个完成的独立验证、诊断和准备工具回合保存会话断点。取消/重启保留缺口、动作、结果、轮次和下一步；独立验证已执行的命令也保留。条件一致时接续未完成阶段；源码、基线或执行配置变化则丢弃旧会话，重新独立读取和检查。中断回合不会盲目重放；已写入文件先从实际工程核对。旧版空结果/空缺口状态按原验收项重建缺口，不能静默暂停为空白原因。
- 命令保存退出码、输出、执行时间、耗时及源码指纹。指纹覆盖整个源码树和锁文件，不受界面 600 个文件列表上限限制；依赖目录、构建输出、缓存与 `.runtime` 证据目录排除。独立验证结果与该指纹关联，最终人工验收前再次核对源码及确认范围。
- 兼容既有工程在 `verification/<子目录>`、`test-results/<子目录>`、`playwright-report/<子目录>` 下生成的图片/视频，以及包含 `sourceAndBuild` SHA256 清单、开始时间和执行状态的 JSON 运行记录。这些生成物不会触发“源码变化”；普通配置 JSON、范围 README、测试脚本仍参与指纹，不能把整个 verification 目录排除。
- 验证模型每轮接收当前命令台账，避免长工具历史压缩后遗忘已执行的检查。非结构化的结论最多进行一次无工具格式整理；格式整理不能运行新检查或把历史记录变成新证据。
- 验证报告分开记录 `unit / mock / application / desktop / duration / history / inspection`，通过项关联本轮命令 ID。实机/桌面/时长类型必须与执行记录相符，报告实测时长不能超过命令实际运行时间。仅核对历史记录不能作为当前运行通过依据。旧格式无类型记录不自动升级为实机证据。
- 证据类型仍需独立验证者根据真实输出判断；类型标签本身不会给命令增加桌面观察能力。准备阶段测试输出属于准备记录，最终判断必须使用独立验证重新执行的输出。
- 一个真实执行可以用 `evidenceKinds` 同时声明应用运行和短时测量，避免为类型标签重复运行同一检查。`history` 与其他标签混用时仍只按历史核对处理；时长上限仅计算声明实际测量的命令。
- 对现有标准中明确的托盘、任务栏、原生菜单等鼠标/悬停/菜单交互，应用 API 或菜单回调报告不能直接通过；即使标成 `desktop`，报告若承认缺少实际输入也保留未验证。旧版未完成交付中的此类通过记录会保留原文并恢复未验证，不重置修复/准备预算，也不改动已经最终人工验收的功能。这是保守的证据校验，不是通用桌面自动化驱动，也不能替代检查脚本真实性的独立审查。
- 面向用户的结论以系统实际判定为准，不能继续显示模型“全部通过”的矛盾总结或内部结果 JSON；真实检查失败和缺条件仍分开展示。存在未解决失败时，准备面板顶部列出失败命令，不能被缺口摘要遮盖。
- 同一源码版本尚未解决的实际失败，在下一轮没有执行检查、或者只执行其他成功检查时仍保留，并继续关联此前失败的验收项。只有对应检查实际复验成功，或源码变化后重新取得证据，才会替换旧记录。保留记录沿用原时间戳，ID 标明 `unresolved-`，不冒充本轮新执行。执行策略版本变更会使旧会话失效，原修复/准备预算不重置。

数据复用 `Feature.verificationPreparation`、`verificationChecks`、主进程执行断点、活动记录和既有执行计划。没有新增并行修改目标工程的执行器。

## 回归入口与证据范围

### 2026-09-28 路由与证据修复

已有实际失败时先沿用代码修复流程；到达原 3 轮上限，独立的 unverified 缺口仍进入诊断和准备，不被全局 failedCheck 条件挡住。准备文件变化沿指纹链追溯旧失败，不能冒充业务修复。失败继续阻止成果验收。

准备状态记录当前环境事实及探测时间，断点记录主机环境指纹。环境改变会重新诊断，已完成动作和消耗的准备预算保留。该环境指纹不包含准备自己新增的脚本和依赖，避免正常准备使会话错误失效。Windows UIAutomation/Forms 探测上限为 15 秒；超时属于技术诊断结果，不证明必须人工。

命令台账保存独立 runId，对应 .runtime/verification-evidence 下的同名目录。当前命令的 JSONL started / passed 记录按 mode 配对，将 durationMs、delayMs、observedDelayMs 分别保存为单实例时长、持久化延迟和外部观察延迟。没有本轮 started 的完成记录不成为新测量。并行两个 5 秒不能相加为连续 10 秒，结构化字段直接生成报告。此协议不认证任意 stdout 的真实性，仍须审查实际检查脚本。

当前命令输出明确为 API_CALLBACK_ONLY 时，模型不能将其重标成 desktop 通过；明确断言失败优先于同一输出的技术阻塞标记。日志 review 使用固定摘要，展开正文逐字保留，避免第一行在摘要和全文中重复显示；没有做全局字符串去重。

新增 verification-desktop-preparation.cjs 和 verification-report-smoke.cjs 已加入默认回归。可选 pomodoro-desktop-verification.cjs 使用本地确定性模型夹具驱动生产编排，实际写入补充脚本并独立运行隔离应用，不调用收费模型。详细的原始报告定位、更正、失败及本轮状态见[本轮审计](verification/2026-09-28-native-preparation-audit.md)。

`npm run test:verification` 构建后执行证据/预算回归、验证准备编排、测试进程清理以及真实 Electron 界面检查；这些检查也已加入 `npm test`。

`scripts/verification-live-regressions.cjs` 覆盖真实工程暴露的空诊断恢复、多级命令、报告/源码分离、非结构化报告整理，以及验证命令在连接中断和重启后的恢复。`npm run test:verification:live-pomodoro` 是显式选择的真实模型集成检查：复制现有番茄钟工程和加密连接资料，在隔离副本调用现有模型并执行检查，核对原项目文件未变，不提交最终人工验收。该入口会使用现有模型服务，默认 `npm test` 不包含它。

该入口支持 `--resume .runtime/pomodoro-live-verification/run-<id>` 继续已停止的同一副本和断点；仍保留 15 分钟有界运行及原准备/修复预算。只检查已有结果和界面时使用 `node scripts/pomodoro-live-verification.cjs --capture --resume <run目录>`，不调用模型、不重新执行目标测试，单独保存策略复核快照，不能把它当成新实测。真实线上番茄钟复测、实际失败和证据边界见[番茄钟实测记录](verification/2026-09-28-pomodoro-live.md)。

- `scripts/verification-preparation.cjs`：确定性模型回复驱动真实 service、store、文件工具及命令。脚本实际写入临时项目，再由独立验证执行真实断言；开发依赖实际通过 npm 安装项目内离线包。覆盖混合缺口、缺陷路由、无进展、预算、取消、恢复、源码/锁文件变化及角色边界。
- `scripts/verification-processes.cjs`：启动真实短时子进程，检查取消、宿主突然退出后的进程终止与重启清理。
- `scripts/verification-preparation-smoke.cjs`：真实 Electron、IPC、持久化与本地协议夹具，检查三个准备子阶段、实际生成与执行脚本、剩余外部缺口、重启继续、键盘、明暗主题及 1280×840 / 860×600 布局。

以上结果不等于收费模型的开放式任务成功率、npm 公网安装质量或任意目标应用的真实桌面验收。未通过此回归宣称跨平台桌面自动化、长时间测量或用户最终验收完成。

初始实现验证见[2026-09-28 验证记录](verification/2026-09-28-verification-preparation.md)。后续番茄钟真实运行、由实测发现的问题修复、最终构建指纹和分段回归结果见[番茄钟实测记录](verification/2026-09-28-pomodoro-live.md)；旧记录不是新版本自动通过的依据。
