# 圆桌讨论与多端项目规划

## 使用

1. 在「需求与功能图 → 需求」切换到「圆桌讨论」，选择 2–6 个已配置模型并填写职责。第一个勾选的模型负责最终汇总。默认每轮模型进行两次讨论：提出方案、交叉评审，再由主持人整理。
2. 在输入区提出议题并发送。模型依次读取完整讨论、其他成员观点、项目需求和共享上下文；发言实时显示模型、职责、轮次、文本、实际思考与工具调用。各模型随讨论更新功能图，需要人工取舍时即时弹出决策卡，可选择、输入想法或「后面再说」。
3. 主持人整理完整需求文档、子项目及功能后，状态变为「等待人工反馈」。系统停在这里，不自动开启下一轮。输入人工反馈并发送后，参会模型继续讨论下一轮；配置可以在两轮之间调整。
4. 方案满意后点击「审阅完整方案」。审阅完整需求、子项目职责/接口、功能及验收标准，再「确认并保存基线」。人工确认后进入已有功能方案流程，代码开发仍按功能串行推进。

每轮可选 1–3 次模型讨论，之后都有一次主持人汇总阶段；所有发言阶段都可以包含工具续接。需要人工取舍时立即插入决策卡，不等到最后收集一批问题。失败或停止会保留已经收到的发言和已整理的草稿，不将本轮标为已确认。不存在无人值守的无限讨论循环。

## 讨论中的决策卡与功能图

参会模型遇到范围、体验、成本等需要人类取舍的问题时，通过 `ask_human` 提出一张决策卡。卡片显示问题、影响、发言者和最多四个建议选项，可以选择并补充，也可以直接输入自己的想法。底部始终有「后面再说」。每次只处理一张，当前模型等待回答时不再发起请求，没有自动超时替人作答。

卡片出现在讨论区域内，不遮挡旁边功能图，不使用全屏遮罩；可收起继续看图，再从「1 项待你决定」打开，也可停止圆桌。窄窗口中卡片正文独立滚动，提交和暂缓按钮保持可见。输入草稿保存在本机。

选择「后面再说」会记录为暂缓并继续当前讨论，把问题及背景传给后续模型。其他参会模型可以通过 `resolve_deferred_decision` 给出有理由的建议；提出问题的模型不能立即自行撤销暂缓。仍不能确定的事项继续保留为未决，不能把暂缓当成同意。普通人工答案不能被该工具覆盖。模型建议和人工决定在「决策记录」中明确区分，也会出现在完整方案的审阅资料中。

各参会模型都可以使用 `update_project_targets`、`update_features`、`update_requirements` 等需求工具。每次完整、校验通过的工具调用立即保存并更新功能图、子项目及独立预览窗口；不会把流式传输中尚不完整的工具参数当作有效功能，也不等最后主持人汇总。提示要求模型先同步已经明确的部分，再提出依赖人工答案的问题，以小步工具调用持续整理。

决策卡跨停止与重启保留。运行中的卡片提交后接续原工具会话；若应用已经停止或重启，提交后从记录的当前发言阶段重新读取完整上下文继续，已完成的前序发言阶段不重跑。存在待决卡时不能另起一轮绕过它。启动应用本身不会自动调用模型。

## 一个产品，多个子项目

现有顶层工程作为同一个产品方案和共享工作区；「子项目」描述需要分别开发的端，不是另起互不知情的工程。

- 支持前端 Web、后台服务、管理后台、移动端、桌面端、IoT / 设备和其他类型。
- 每个子项目有稳定标识、名称、类型、规划目录、职责边界、接口与共享数据约定。
- 每项功能关联所属子项目。不同端可以存在同名功能，不会因为标题相同而合并。跨端协作通过接口约定与功能依赖记录。
- 普通单模型讨论同样能够建立子项目。模型调用 `update_project_targets` 后，再通过 `update_features` 的 `targetId` 关联功能。也可在「子项目」中手动新增/编辑，在功能详情中调整归属。
- 存在子项目时，本期功能必须明确归属才能确认完整需求。已确认子项目有功能进入后续阶段时不能直接重写边界；未开发的功能可先「继续修订」。

子项目目录在需求期是规划，不自动创建代码、仓库或安装依赖。多端架构、业务范围与接口可以在此讨论和确认；当前工程执行工具仍主要面向本机 Node/npm 工程，原生移动端编译、固件烧录和设备调试工具链尚未扩展。

## 多视窗

整体功能图按「子项目 → 模块 → 功能」分层。预览顶部可选择整体方案或单个子项目。

「子项目」卡片的「功能窗口」「原型窗口」分别打开原生独立窗口。窗口以顶层工程、子项目、面板类型区分，同一面板重复打开会聚焦已有窗口，不同子项目可以同时保持可见。窗口实时读取同一份工程数据，关闭窗口不会删除记录。

设计原型时可以指定子项目；该子项目只显示自己的原型版本和设计过程，不把其他端的原型混进来。同一顶层工程仍最多同时运行一次原型生成，可以在生成时继续需求讨论。HTML 原型是设计材料，不代表移动端或设备代码已实现。

## 本地记录

主数据继续保存在 `engineering-v1.json`，新增字段向后兼容。原有工程没有子项目时仍按原来的单项目方式使用。

模型接收的历史 AI 发言作为带原模型身份、职责与轮次的讨论资料传入，明确区分人工指令与模型观点，不冒充当前模型自己的原生回复。当前请求中的工具调用及续接则原样保留协议所需的思考内容、签名或响应项。这样切换供应商、主持人汇总和重启后继续讨论时，都能读取完整记录，不依赖其他模型的思考协议。界面中的原始发言、思考展示和工具记录继续保留。

- `Project.targets`：子项目规划；`Feature.targetId`、`PrototypeRevision.targetId`：归属。
- `Project.roundtable`：当前会议配置、轮次、阶段、人工等待或错误状态。
- `Project.chat`：完整的人类与模型讨论；圆桌消息附加 `meetingRound`、`speaker`、模型身份。
- `Project.decisions`：问题、选项、提出者、人工答复、暂缓状态及模型解决建议；`Project.roundtable.cursor` 保存当前发言阶段。
- `.coprojer/DECISIONS.json`：完整决策记录；人工确认基线时也写入共享上下文。
- `.coprojer/PROJECT_TARGETS.json`、`ROUNDTABLE.json`：结构化本地导出。
- `.coprojer/DISCUSSION.md`：包含职责与轮次的原始讨论；人工确认后，多端边界与功能归属写入共享上下文基线。

验证命令为 `npm run test:research`；`scripts/roundtable-smoke.cjs` 和 `scripts/decision-smoke.cjs` 使用隔离 Electron 资料与本地模型测试服务，覆盖圆桌、实时功能图、逐张决策卡、选项/自由输入/暂缓、跨模型建议、停止/重启接续、子项目与多窗口，以及严格思考协议续接，不消耗真实供应商额度。
